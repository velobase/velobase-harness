# Complete-example subscriptions binding

This module binds `@velobase/subscriptions` to the existing `UserSubscription` and `UserSubscriptionCycle` tables. It selects `@velobase/subscriptions-stripe` for automatic Stripe lifecycle operations and explicitly treats NowPayments as a manual-renewal gateway. Delivery adds the two tables in `prisma/migrations/20260910140000_subscription_deliveries`; existing subscription data is retained. Apply the migration before deploying these services. The normal deploy flow regenerates Prisma Client.

Enrollment is serialized by customer and provider identity; cycle creation is serialized by subscription and unique period key. Revision checks use the existing `updatedAt` value, advancing it monotonically for this adapter's writes. Cycle creation emits `subscription:cycle-created`; the optional Touch module owns reminder scheduling. Subscriptions no longer directly imports the reminder service. The event bus isolates optional notification failures.

Existing fulfillment calls `settleCreate` and `settleCycle` so already accepted business can finish after new subscriptions are disabled. New Admin enrollment and period creation use the gated methods. An automatic subscription requires a remote subscription ID; NowPayments is the explicitly chosen exception.

Customer status reads derive ownership from the session. The old optional `userId` query field remains accepted for compatibility but does not choose the queried account. New owner-scoped list/detail and period-end cancellation procedures are available through the membership router. Direct enrollment and cycle mutation are Admin-only. Customer status retains this host's existing `ACTIVE` relationship policy and plan tier mapping; the shared domain validates period start, expiry and deletion separately.

Immediate cancellation receives the expected owner, asks the provider to cancel, then records cancellation and closes active cycles atomically. Unknown/failed provider outcomes are not swallowed. The subscription upgrade fulfiller awaits this operation and can retry it before creating the new period; it no longer runs a detached cancellation using an unchecked customer-supplied subscription ID. Cancellation emits the domain event consumed by the optional reminder cleanup.

Initial fulfillment and Stripe renewal use `@velobase/subscriptions/delivery`. The host stores the cycle change and immutable delivery plan atomically, then records each credit consumer's receipt. Existing cycle identity and original dates survive retries; timestamps are not used as a proxy for completion. New orders include subscription terms in their product snapshot. These records allow accepted fulfillment to continue after new subscriptions or credits are disabled; they do not change the host's subscription product rules.

NowPayments manual prepayment retains the existing policy: extend the latest active, unexpired cycle, preserve its original start and sequence, and retain its monthly credit cursor. Weekly prepayment schedules the existing weekly grants from the previous expiry; monthly/yearly prepayment does not grant an extra first month. The extension and payment receipt commit together, so replay does not extend the cycle again. The monthly-credit worker retains its existing date arithmetic, snapshot source and scheduling rules; its only module-related change is using the accepted-settlement grant port.

Renewals use the period on verified paid invoice lines. They close only superseded periods, preserve cancellation state and do not revive terminal subscriptions. Missing enrollment can be a webhook race and is retried. Trial-conversion retries recognize the accepted period even after the trial has closed. The existing provider retry and compensation entry points remain; the record service does not start a new queue. Optional notification/affiliate events remain event-bus policies rather than durable delivery receipts.

Legacy fulfilled orders retain their prior completion status. Older unfinished orders that lack plan snapshots use retained subscription terms or the legacy catalog fallback, log that fallback, and freeze it for subsequent delivery. The additive migration does not infer missing historical external receipts. In particular, old manual extensions with an uncertain outcome cannot be reconstructed from an expiry timestamp alone; reconcile those existing exceptions from payment and ledger history.

The complete example still owns subscription Checkout creation, billing portal, support refund policies and the monthly credit worker. The separately selectable Core subscription composition has its own fixed-price policy; it does not replace these existing rules. Changing a feature list does not remove every legacy dependency.

No tests, type checks, lint, builds, application runs, database migrations or provider requests were executed for this extraction.
